The application-data lesson used `sqlite3` with repositories and migrations. Bigger applications usually add an **ORM** (object-relational mapper): you work with Python objects, and the ORM writes the SQL. **SQLAlchemy** is the standard (Django has its own ORM). This lesson explains how ORMs work inside, so you can use them without the classic performance traps.

## SQLAlchemy 2.0 in brief

```python,norun
from sqlalchemy import ForeignKey, String, create_engine, select
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column, relationship, Session, selectinload

class Base(DeclarativeBase):
    pass

class Team(Base):
    __tablename__ = "teams"
    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(50), unique=True)
    members: Mapped[list["User"]] = relationship(back_populates="team")

class User(Base):
    __tablename__ = "users"
    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str]
    team_id: Mapped[int] = mapped_column(ForeignKey("teams.id"))
    team: Mapped[Team] = relationship(back_populates="members")

engine = create_engine("sqlite:///app.db", echo=True)     # echo prints every SQL statement
Base.metadata.create_all(engine)                            # real apps use Alembic migrations

with Session(engine) as session:
    ops = Team(name="ops", members=[User(name="maya"), User(name="li")])
    session.add(ops)
    session.commit()

    stmt = select(Team).options(selectinload(Team.members)).order_by(Team.name)
    for team in session.scalars(stmt):
        print(team.name, [u.name for u in team.members])
```

- Models are classes with typed `Mapped[...]` columns; `relationship` links objects.
- **Alembic** generates and runs migrations from model changes (`alembic revision --autogenerate`, `alembic upgrade head`).
- With **asyncio**: `create_async_engine("postgresql+asyncpg://...")` and `AsyncSession`.
- **SQLModel** combines SQLAlchemy models with Pydantic, popular with FastAPI.

## The session: unit of work and identity map

The **Session** is the heart of an ORM. Two patterns make it work:

1. **Identity map**: within one session, each database row is loaded as **exactly one** Python object. Loading user 7 twice returns the same object, so changes made through one reference are seen through the other.
2. **Unit of work**: the session tracks new, changed ("dirty") and deleted objects. Nothing is written immediately; on `commit()` (or `flush()`) it writes all changes in one transaction, in a safe order (parents before children).

Consequences:

- Keep sessions **short**: one per request or per job. A long-lived session holds stale objects and grows forever.
- After `commit()` objects are expired and reload on next access.
- An exception before `commit` means nothing was written; call `rollback()` (or use `with session.begin():`).

The first exercise builds a tiny identity map and unit of work over `sqlite3`.

## Lazy loading and the N+1 problem

By default, `team.members` is loaded **lazily**: the first access runs a query. That's convenient, and a trap:

```text
teams = session.scalars(select(Team)).all()   # 1 query
for t in teams:
    print(len(t.members))                      # +1 query PER team
```

With 500 teams that's **501 queries**: the **N+1 problem**, the most common ORM performance bug. Fixes:

| Strategy | SQL | Use when |
|---|---|---|
| `selectinload(Team.members)` | 1 query for teams + 1 `WHERE team_id IN (...)` | one-to-many collections (usual default choice) |
| `joinedload(User.team)` | a single JOIN | many-to-one (each user's team) |
| an aggregate query | `GROUP BY` | you only need counts or sums |

Turn on `echo=True` (or SQL logging) in development and **count your queries**. Django has `select_related` / `prefetch_related` for the same purpose. The second exercise demonstrates N+1 vs batching with plain SQL.

## When to skip the ORM

ORMs shine for CRUD and domain objects. For reports, analytics, bulk updates and complex window functions, write SQL directly: SQLAlchemy Core (`select(...)` without mapped objects) or `text("...")` with parameters. Mixing both is normal.

## Connection pools and transactions

- An **engine** keeps a pool of database connections; reuse one engine per process.
- **Isolation levels** control what concurrent transactions see (see the SQL track); Postgres defaults to READ COMMITTED.
- For "check then update" logic (stock, seat bookings) use row locks (`with_for_update()`) or optimistic locking (a version column).

@@solution
import sqlite3


class User:
    def __init__(self, id, name, active):
        self.id = id
        self.name = name
        self.active = active


class Session:
    def __init__(self, conn):
        self.conn = conn
        self.identity = {}
        self.original = {}
        self.new = []
        self.queries = 0

    def get(self, user_id):
        if user_id in self.identity:
            return self.identity[user_id]
        self.queries += 1
        row = self.conn.execute("SELECT id, name, active FROM users WHERE id = ?", (user_id,)).fetchone()
        if row is None:
            return None
        user = User(*row)
        self.identity[user.id] = user
        self.original[user.id] = (user.name, user.active)
        return user

    def add(self, user):
        self.new.append(user)

    def commit(self):
        inserted = updated = 0
        with self.conn:
            for uid, user in self.identity.items():
                if (user.name, user.active) != self.original[uid]:
                    self.conn.execute("UPDATE users SET name = ?, active = ? WHERE id = ?", (user.name, user.active, uid))
                    updated += 1
            for user in self.new:
                cur = self.conn.execute("INSERT INTO users (name, active) VALUES (?, ?)", (user.name, user.active))
                user.id = cur.lastrowid
                inserted += 1
        for user in self.new:
            self.identity[user.id] = user
        self.new = []
        for uid, user in self.identity.items():
            self.original[uid] = (user.name, user.active)
        return inserted, updated


conn = sqlite3.connect(":memory:")
conn.execute("CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT, active INTEGER)")
conn.executemany("INSERT INTO users (name, active) VALUES (?, ?)", [("maya", 1), ("li", 1), ("sam", 0)])

b = s.get(1)

import sqlite3


class CountingConnection:
    def __init__(self, conn):
        self.conn = conn
        self.count = 0

    def execute(self, sql, params=()):
        self.count += 1
        return self.conn.execute(sql, params)


def members_naive(conn):
    result = {}
    for team_id, name in conn.execute("SELECT id, name FROM teams").fetchall():
        rows = conn.execute("SELECT name FROM users WHERE team_id = ?", (team_id,)).fetchall()
        result[name] = sorted(r[0] for r in rows)
    return result


def members_batched(conn):
    teams = conn.execute("SELECT id, name FROM teams").fetchall()
    by_id = {team_id: [] for team_id, _ in teams}
    if by_id:
        placeholders = ",".join("?" * len(by_id))
        rows = conn.execute(f"SELECT team_id, name FROM users WHERE team_id IN ({placeholders})", list(by_id)).fetchall()
        for team_id, name in rows:
            by_id[team_id].append(name)
    return {name: sorted(by_id[team_id]) for team_id, name in teams}


def member_counts(conn):
    rows = conn.execute(
        "SELECT t.name, COUNT(u.id) FROM teams t LEFT JOIN users u ON u.team_id = t.id GROUP BY t.id ORDER BY t.id"
    ).fetchall()
    return dict(rows)


def make_db():
    db = sqlite3.connect(":memory:")
    db.executescript("""
        CREATE TABLE teams (id INTEGER PRIMARY KEY, name TEXT);
        CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT, team_id INTEGER);
        INSERT INTO teams (name) VALUES ('ops'), ('dev'), ('sec');
        INSERT INTO users (name, team_id) VALUES ('maya', 1), ('li', 2), ('sam', 1), ('kai', 2), ('zoe', 2);
    """)
    return CountingConnection(db)


c = make_db()
print(members_batched(c), c.count)
c = make_db()
print(member_counts(c), c.count)
